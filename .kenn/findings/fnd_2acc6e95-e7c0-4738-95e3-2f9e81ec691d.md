DECISION: `@extend %placeholder` (and `@include`/mixin) support is OUT OF SCOPE for the CSS/Sass indexer — not merely deferred for a node kind. Investigated after real-repo validation. `extends_rule` is emitted by a light source scan that only resolves a sole-bare-class enclosing rule (`.btn-primary { @extend .btn }`). Measured on Bootstrap + Bulma, the dominant real-world `@extend` enclosings are exactly the forms the scan cannot resolve: Bulma interpolates every selector (`.#{iv.$class-prefix}name { @extend %block }`) so no sole-bare-class enclosing exists anywhere; Bootstrap extends `%heading` from element selectors (`h1`–`h6`), `%control` from mixins/pseudo-elements. So adding `Kind::CssPlaceholder` + a Sass source-level node producer (placeholders are compiled away by dart-sass, so they're invisible to the compile→parse→source-map pipeline and would need a separate raw-source scan to mint def nodes) would index placeholder nodes yet emit ~ZERO additional edges on the flagship libraries. And because `@extend` is compiled away (styles merge into selector groups like `.btn, .btn-primary {}`, indistinguishable from a hand-written selector list), the compiled output can't recover the relationship either. There is no robust seam. `extends_rule`'s real yield is CSS-Modules `composes` (sole-class by spec, no interpolation, in .module.css app code) and non-interpolated `@extend .class`. Park placeholders/mixins until a concrete codebase with sole-bare-class `@extend %x` justifies it. Captured in css-usage-graph/spec.md (CSS-internal dependency edges requirement + scenario) and design.md risks.
