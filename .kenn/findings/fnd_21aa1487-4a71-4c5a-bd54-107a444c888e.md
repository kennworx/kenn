Do NOT bake a language toolchain version into an indexer image. The toolchain version is a property of the WORKSPACE being indexed, not of the image: every language declares it in a pin file the repo owns (global.json, rust-toolchain.toml, go.mod, Package.swift, .python-version). When the baked version and the pin disagree the run does not fail loudly — it indexes ZERO files and exits 0. Measured on a real 146-project solution: 0 files with an SDK-10-only image against a global.json pinning 9.0.308 (rollForward latestMinor does NOT cross a major, so hostfxr resolves nothing and MSBuildLocator reports only 'no usable MSBuild instance'); 952 files / 15971 symbols / 64763 edges once the pinned major was present.

Shipping N versions per language does not converge — three .NET SDKs cost 1.88GB stripped and still break on the fourth pin. The toolchain is also nearly the whole image: measured payload vs total, kenn-dotnet 28.5MB of 1.03GB (4%), swift 1.75GB of toolchain in a 2.55GB image, rust-analyzer 20.9MB, scip-go 17.3MB, kenn-ts 98MB, scip-python 31MB. Five images totalling 5.56GB carry ~204MB of actual payload.

The direction (see the on-demand-toolchains change): images are FROM scratch — tool binary, the three .so files every one of them links (ld-musl, libstdc++, libgcc_s; libmimalloc-secure for rust-analyzer), and a CA bundle. Toolchains are provisioned HOST-SIDE in Rust into a shared cache volume keyed by resolved version. Host-side is not a preference: rust, go and python run third-party binaries (rust-analyzer, scip-go, scip-python), so there is no sidecar of ours to put provisioning in, and a scratch image has no shell or curl to run an installer with. An unresolvable pin must be FATAL and must name the pin and its source file — never fall back to a present toolchain, because that fallback is the bug.
