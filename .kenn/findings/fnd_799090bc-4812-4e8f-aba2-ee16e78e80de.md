Indexer image bases: ONE glibc distro — ubuntu:noble — for every image. This SUPERSEDES the earlier 'prefer ALPINE, measure before switching' guidance, which optimized the wrong variable. Alpine saved ~450MB across the two images that used it (csharp 187->407MB, typescript 178->404MB measured on arm64) and cost six separate libc-mismatch bugs in one change: a glibc .NET RID provisioned into an alpine container, a musl entrypoint COPYed onto a debian base, rust-analyzer publishing gnu-only, Node publishing no musl build at all. EVERY one presented identically — a binary that exists on disk and will not exec, with a bare 'not found' naming neither the file nor the reason. That diagnostic cost dwarfs the megabytes.

NOBLE specifically, not debian: the swift image must be FROM swift:6.3-noble-slim (the vendor's toolchain needs GLIBC_2.38 and is the one base we do not choose), so matching it everywhere keeps a single glibc floor of 2.39 instead of a debian/ubuntu split. ubuntu:noble is 27.6MB against debian:bookworm-slim's 26.8MB — ubuntu publishes no -slim tag because its base already IS the slim one; the correct debian analogue is bookworm-slim, never bookworm (46MB).

BUILDER stages are exempt and may sit BELOW the runtime floor, never above: rust:1-slim-bookworm builds the shared entrypoint (no official rust:*-noble exists), and the go/node sidecars are bookworm too. A 2.36 build runs on a 2.39 runtime; the reverse does not. Raising a builder's glibc above the lowest consuming runtime is the same 'exists but will not exec' bug wearing a different hat.

Verify a base swap by INDEXING A REAL REPOSITORY CLONED FROM GITHUB, never by --version. Verified on noble: serilog/serilog 3444 symbols, google/uuid 329, BurntSushi/byteorder 517, psf/requests 728, colinhacks/zod 4707, apple/swift-argument-parser 5699.
