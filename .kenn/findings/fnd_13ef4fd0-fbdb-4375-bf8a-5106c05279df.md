kenn-swift Xcode mode (`Provisioning.swift`) — VALIDATED on real apps: Ice (macOS), Food Truck (iOS), Toast-Swift+SwiftyJSON (CocoaPods). The SwiftPM/Xcode/CocoaPods split is entirely in Provisioning; `Indexer.swift` reads any libIndexStore store unchanged.

Build recipe (deterministic, signing-free):
  xcodebuild build -project X.xcodeproj|-workspace X.xcworkspace -scheme S \
    -destination 'generic/platform=iOS Simulator'|'generic/platform=macOS' \
    -derivedDataPath <local> -skipPackageUpdates \
    CODE_SIGNING_ALLOWED=NO COMPILER_INDEX_STORE_ENABLE=YES \
    ENABLE_USER_SCRIPT_SANDBOXING=NO
  → read <local>/Index.noindex/DataStore

Key points:
- LOCAL `-derivedDataPath` (under `<workspace>/.kenn/local/xcode-dd/<name>-<hash>`): deterministic store path, avoids hashed/sandbox-unreadable global DerivedData.
- `ENABLE_USER_SCRIPT_SANDBOXING=NO` is REQUIRED for CocoaPods: Xcode 15+ sandboxes run-script phases and denies the embed-frameworks `rsync` ("Sandbox: rsync deny"). We only need the compile (which writes the store), not the embed, so disabling it is safe.
- `.xcworkspace` is built with `-workspace` and wins over a co-located `.xcodeproj` (CocoaPods/SwiftPM). Scheme via `xcodebuild -list -json` (container-named, else first). Destination auto-detected from `SUPPORTED_PLATFORMS` (macOS preferred); `--platform` overrides for MULTIPLATFORM apps (auto-detect would pick macOS).
- iOS needs the SIMULATOR RUNTIME installed (SDK alone is not enough): `xcodebuild -downloadPlatform iOS` (~8.5 GB). A stale post-update Xcode (plugin load failure) is fixed by `xcodebuild -runFirstLaunch`.
- A project with a pre-existing per-config base xcconfig (e.g. Apple's Food Truck) can leave `${PODS_ROOT}` undefined → CocoaPods `Unable to load file list /Target Support Files/...`. That's a CocoaPods/project quirk (plain `xcodebuild` fails identically), NOT a kenn issue.
