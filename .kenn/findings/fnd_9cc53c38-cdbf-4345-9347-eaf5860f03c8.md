Sass source-map back-mapping mechanism (`css/sass.rs::compile_and_extract`): compile each entry to a scratch file under `<ws>/.kenn/local/sass-build/<hash>.css` with `sass --style=expanded --quiet --source-map [--load-path=<ws/lp>]… <entry_abs> <out>` (NOT to stdout — dart-sass only emits a source map when writing to a file). Parse the compiled `.css` with `collect_atoms`; each Atom carries 0-based `line` AND `col` (lightningcss `loc.column` is 1-based → subtract 1) so `sourcemap::SourceMap::lookup_token(line, col)` resolves the right token when several rules share a line. `token.get_source()` is relative to the `.map` file's dir, so resolve via `out_dir.join(src).canonicalize()` then strip the canonicalized workspace root → the origin `.scss` relpath (skip if outside the workspace); `token.get_src_line()` is 0-based → +1 for the def line. dart-sass handles `.sass` (indented) and `.scss` identically — no special path. Generated classes (`@each`/mixins) all back-map to the loop/mixin line, so their def-site granularity is coarse (expected, documented).
