VALIDATED end-to-end (spike on Ice/macOS + Food Truck/iOS): kenn-swift's SwiftPM/Xcode split is entirely in `Provisioning.swift` — the index store is the same libIndexStore format whichever build system produced it, so `Indexer.swift` reads an Xcode store unchanged.

Xcode mode recipe (deterministic, signing-free):
  xcodebuild build -project X.xcodeproj -scheme S \
    -destination 'generic/platform=iOS Simulator'   # or 'generic/platform=macOS'
    -derivedDataPath <local> CODE_SIGNING_ALLOWED=NO COMPILER_INDEX_STORE_ENABLE=YES
  → read <local>/Index.noindex/DataStore

Key points learned:
- Use a LOCAL `-derivedDataPath` — makes the store path deterministic and avoids the hashed global `~/Library/Developer/Xcode/DerivedData/<Proj>-<hash>` (also sandbox-unreadable). Store is `<dd>/Index.noindex/DataStore`.
- iOS needs the SIMULATOR RUNTIME installed (SDK alone is not enough): a build with no eligible destination errors `iOS X.Y is not installed`; fix with `xcodebuild -downloadPlatform iOS` (~8.5 GB).
- `xcodebuild` itself can be broken after an Xcode update (plugin load failure, e.g. `IDESimulatorFoundation` → stale `/Library/Developer/PrivateFrameworks/DVTDownloads.framework`); fix with `xcodebuild -runFirstLaunch`.
- `--workspace` scoping excludes SPM deps checked out under `<dd>/SourcePackages` automatically (verified: 0 dep files leaked).
- `swift build` cannot build an `.xcodeproj` (no Package.swift) — separate build systems, not a kenn limitation.
- The `--store <path>` sidecar flag (bypass provisioning, read any store) is the read-primitive Xcode mode builds on. Cosmetic noise on real apps: SwiftUI `#Preview` macro emits `$s…`-mangled key names; an occasional computed-property `getter:` leaks as an edge endpoint — both filterable.
