Do NOT drain a redirected child process's stdout/stderr with `CopyToAsync` in kenn-dotnet. Use a blocking `CopyTo` on its own thread (`SolutionLoader.StartBlockingDrain`, `TaskCreationOptions.LongRunning`).

On macOS an async read of a redirected pipe completes through SocketAsyncEngine's kqueue loop. A completion that lands after `CopyToAsync` has returned its buffer to the ArrayPool corrupts that buffer, and the process dies with a fatal, uncatchable AccessViolationException inside `PipeStream.ReadAsyncCore` on a threadpool thread — taking the whole index run with it. Measured at 11 aborts / 20 runs when regressed; 0 / 32 with blocking reads; 0 / 18 with --skip-restore (RunRestoreAsync never entered).

Use LongRunning, not Task.Run: the read blocks until the child's pipe EOFs, capped at RestoreTimeoutMs (5 min default). Two parked threadpool workers would starve the Roslyn project loads sharing that pool, which grows by roughly one thread per second past the core count.

GUARD: `just index-stability` runs the index 8 times and fails on any "Fatal error". The property is probabilistic, so no unit test can assert it — 8 runs miss a 50% regression with probability 0.4%. Mutation-verified: reverting to CopyToAsync makes the gate report 5/8 aborts and exit 1.

This was misattributed for a long time to a lingering Roslyn BuildHost, and BuildHostGuard exists because of that theory. The theory is wrong: `pgrep -f BuildHost` is empty immediately before a crashing run, and the crash lands between the "$ dotnet restore" log line and the exit-code check. BuildHostGuard still earns its keep sweeping orphans that hold NuGet locks and obj handles, but it is not what prevents the AVE. When an AVE appears here, look for an async read on a pipe whose stream is about to be disposed.
