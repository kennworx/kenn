A test that a limit does NOT apply is vacuous unless the fixture would trip that limit. Before claiming a mutation check guards a "must not bound / must not re-rank" rule, verify the fixture can distinguish the two outcomes — otherwise the mutation passes and you have recorded a guarantee you never tested. Two forms, both hit while pinning the atlas tables axis: (1) THRESHOLDS — the render caps MAX_TABLES=40, MAX_TABLE_FILES=12, MAX_REFS_PER_FILE=6 live in atlas/producer.rs and must never bound the query in kenn-mcp/src/tools/tables.rs; against the one-table/two-reference fixture the axis shipped with, moving every cap into the query changes nothing and all three mutations pass. The guard only exists because wide_table_workspace is built past all three (45 tables, one named from 15 files, 8 of those in a single file). (2) ORDERING — the query must rank by the shared atlas/tables.rs selection, not re-sort. That is only checkable if the correct order differs from the order a plausible bug produces: the fixture names the widest table t45 precisely because it is LAST alphabetically and FIRST by breadth, so a name-sort mutation answers t01. Had the widest table been t01, the same mutation would have produced the right answer for the wrong reason and survived. Corollary for capped surfaces: assert the pre-cap totals AND the enumerated list separately — under a cap mutation the totals stayed correct while the list silently truncated, which is exactly the shape that reads as a complete answer.
