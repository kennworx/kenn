A C# extension method (`static void Foo(this Order o)`) is keyed to its HOLDER static class, not the receiver — Roslyn's model, and correct (`PubId.ForMember` uses `member.ContainingType`; a reduced call `o.Foo()` is walked back via `ReducedFrom` to the holder). So `list_in_scope(Order)` does NOT show extension methods.

To make extension methods discoverable FROM the type they extend, the producer emits an `extends_type` edge (method → receiver type) in `EmitMethodRelationships`: when `method.IsExtensionMethod`, target `method.Parameters[0].Type.OriginalDefinition` (the `OriginalDefinition` so a generic `this IEnumerable<T>` attaches to the open `IEnumerable<>`). The method KEEPS its `defined_in → holder`; the type's extension methods are its INCOMING `extends_type` edges (`find_usages(type, edge_kinds:[extends_type])`).

Do NOT "fix" extension discovery by (a) re-keying the method to the receiver type — that corrupts `defined_in`/`parent`; or (b) reusing the `type_use` edge the `this` param already emits — a type's incoming `type_use` is every method that takes it as ANY parameter, indistinguishable from the `this` receiver. A dedicated `extends_type` edge is the only clean signal. (Swift is the opposite: extension members key to the extended type natively, so Swift needs no `extends_type`.)
