Sass indexing perf: dart-sass compilation (a subprocess per entry) dominates SCSS index time; lightningcss/`.css` is Rust-bound and ~instant. Optimization implemented (`css/sass.rs::compile_and_extract_batch`): compile ALL entry points in ONE dart-sass invocation using the CLI's `input:output` pair syntax (`sass --source-map a.scss:a.css b.scss:b.css …`), amortizing the ~per-spawn startup. If the batch exits non-zero (one bad entry sinks the whole invocation and dart-sass doesn't say which), fall back to per-entry `compile_and_extract` to isolate + skip the broken file (preserving the 4.5 skip-broken guarantee). Measured via `kenn index` on real corpora (release): Bootstrap 4 entries 1.6s→0.75s; Bulma 64 entries 6.5s→~2.6s (64 spawns→1); node/edge counts byte-identical before/after. Note `is_sass_entry` (non-`_`-prefixed) over-counts entries for Bulma (64 — many `sass/` files meant to be `@use`d, not standalone); batching makes that cheap. Release vs debug: ~4× on `.css` (Rust), negligible on SCSS (dart-sass is external/native).
