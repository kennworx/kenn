Package-level coupling has ONE implementation, in kenn-indexer::atlas::coupling, used by both the atlas producer and the `packages` query (kenn-mcp tools/packages.rs, surfaced as `kenn packages`). The two start from different inputs — the producer from the in-memory graph mid-index, the query from aggregate_nodes/aggregate_edges rows of a published snapshot — but every RULE lives in the shared module: what counts as a dependency, how relations split, the render caps (MAX_DEPS 8 outgoing vs MAX_DEPENDENTS 24 incoming), and the role thresholds. Two copies of a threshold is how a CLI and a document start disagreeing about the same repo, and a user cannot tell which one lied.

The query reads the AGGREGATE graph, never re-projecting per-symbol edges: it is already rolled up and weighted, and it is the same input the atlas builds from, so the numbers match by construction rather than by luck. Three filters are load-bearing and each has a mutation-checked test: external nodes are vendored dependencies and `<unanchored>` is the no-package sentinel — counting either invents packages the repo does not have; and test-dominance requires a strict MAJORITY (tests * 2 > total), matching the atlas rule, so an evenly-split package is not filed under tests.

Bare `kenn packages` returns counts only; a named package adds its full coupling both directions. That asymmetry is deliberate — emitting every package's couplings is quadratic and unreadable on a 125-package solution. The pure computation is `package_views(nodes, edges, want)`, so the async tool is a thin I/O shell and the rules are testable without a published snapshot behind them.
