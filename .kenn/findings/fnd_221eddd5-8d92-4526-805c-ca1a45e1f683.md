The `just crap-ci` flake has a CAUSE and a workaround: run it serialized. Observed five times in one session with a different offender set each run (250 entries, then 5, then 57), always the same signature — functions in crates the change never touched, at exactly `coverage: 0.0`, usually with no failing test to explain it. `RUST_TEST_THREADS=1 just crap-ci` passed immediately after two consecutive parallel failures on identical code. The mechanism is parallel test execution under llvm-cov: some binaries' profraw data does not land, so their functions read as wholly uncovered and the gate reports them as new-over-threshold. The same parallelism intermittently fails the embedder-dependent tests in kenn-store's hybrid_search (they pass in isolation and in a serialized run), which is a second symptom of the same thing rather than a separate bug.

DIAGNOSE BEFORE BELIEVING A FAILURE, and do not draw conclusions from small samples: comparing one stashed run against one changed run wrongly implicated an unrelated two-file change until a third run contradicted it. Count statuses and the coverage distribution instead, then re-run serialized. This SUPERSEDES the earlier guidance to simply re-run — re-running unserialized can fail repeatedly with a different offender set each time, which reads like a real and moving regression. Still never run `just crap-baseline` to silence it (CLAUDE.md section 6).
