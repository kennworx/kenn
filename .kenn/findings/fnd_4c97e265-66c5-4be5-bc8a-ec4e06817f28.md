Do NOT hand-roll a Sass parser or a tolerant fallback scanner for `.scss`/`.sass`. A spike showed every off-the-shelf option is wrong or incomplete: tree-sitter-scss 1.0 lacks `!default`/`@use as` (21k+ ERROR nodes on Bootstrap, and errors corrupt nearby nesting); grass lags the Dart-Sass stdlib (fails Bulma's `color.channel`); lightningcss has no Sass support. The decision: `.scss`/`.sass` MUST be compiled by the dart-sass compiler (discovered from `node_modules/.bin/sass`, the `sass`/`sass-embedded` npm packages, then PATH, then a bundled binary — via the stable CLI, NOT the `sass-embedded` Rust crate which is protocol-stale and panics on modern dart-sass), then the compiled CSS is parsed by lightningcss (this also captures `@each`/mixin-GENERATED classes a source scan can never see). An entry that fails to compile is skipped+logged, never partially scanned. A degraded mode, if ever needed, reuses lightningcss error-recovery over raw source — not new parser code. Today (`css/ingest.rs`) `.scss`/`.sass` are discovered but skipped with an info log until this compile path lands.
