Inline markdown links `[t](path)` are written RELATIVE TO THE LINKING FILE, so `resolve_inline` must join the target onto the linking file's directory and normalize `.`/`..` into a workspace-relative path, then look it up by_path BEFORE falling back to the bare basename. resolve_link therefore takes the linking file's relpath (threaded from `FileState.relpath`). The order is: exact-as-written → relative-to-linking-dir (both Exact) → basename stem (Drifted) → dangling. Without the relative step, every `[x](../foo/bar.md)` misses by_path and collapses to by_stem("bar") — catastrophic on real repos that mirror the same filenames across many dirs: indexing github.com/affaan-m/ecc (2410 md files, 868 named SKILL.md) went from 72316 links_to edges / 71692 ambiguous (one section fanned to 4340 edges) to 7006 / 5634 with the fix — exact 286→1200, ambiguous −92%. `join_relative` is pure string math (no FS); `..` above the root returns None (target not in corpus → basename fallback). The residual ambiguity is genuine (bare-name/wikilink refs to truly-duplicated filenames), which keep-all correctly preserves.
