When MSBuildLocator fails, suspect the INDEXED REPO's global.json before blaming the host. The old diagnostic told the user to install the .NET SDK and put 'dotnet' on PATH — both of which were already true; the actual cause was the workspace pinning an SDK major the toolchain did not carry, which surfaces only as 'Error while calling hostfxr'. MsBuildBootstrap.FindSdkPin walks up from the workspace for the NEAREST global.json (nearest wins even when it carries no sdk block — that is what the SDK resolver does, so reporting a farther pin misdirects) and FormatReason quotes the pinned version, its rollForward mode, and the file.

Search from opts.Workspace, NOT the process cwd — they differ whenever the caller passes --workspace, and the pin that matters belongs to the repo being indexed.

Constraints this must not break (see the MSBuild-registration directive): the diagnostic stays on Console.Error.WriteLine and never ILogger, because KENN_DOTNET_LOG=Critical silences LogError and this is the only output a user without a working SDK ever sees; registration stays in the index action; IndexCommand.Run keeps [MethodImpl(NoInlining)]. Both new guards were mutation-verified — removing the pin lookup makes FormatReason_NamesTheGlobalJsonPinInsteadOfBlamingPath fail on the missing version string.
