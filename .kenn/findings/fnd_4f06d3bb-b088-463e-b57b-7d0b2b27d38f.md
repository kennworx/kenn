An atlas concept id is a FILENAME and a markdown link DESTINATION, so it must be built from an allowlist: alphanumerics (Unicode-aware) plus `_` `-` `.` `@` — the four marks real package names carry (`kenn-store`, `Acme.Billing`, `platform-socket.io`, `@nestjs/core`). Everything else, path separators included, maps to `_`, runs collapse, and neither end may keep a `_` or `.`.

Two defects this closes, both found by reading filenames rather than by any test. A Swift package anchored on `ArgumentParser/Parsable Properties` was written to `swift_ArgumentParser_Parsable Properties.md` and linked as `](/packages/… Parsable Properties.md)` — an unescaped space TERMINATES a link destination in CommonMark, so the file existed on disk while every markdown reader saw a broken link. And `:` `<` `>` `"` `|` `?` `*` are illegal in Windows filenames, which this project targets; a denylist would have to enumerate them and would still miss the next one.

VERIFICATION LESSON, the important half: a bundle checker that resolves each `](...)` against the filesystem CANNOT see this class of bug. It reported "362 link targets, 0 dangling" while two of those links were broken as markdown. Check link destinations for hostile CHARACTERS as well as for existence — `verify-atlas.sh` does both, and the character check is the one that catches it.

Also: reject a producer-supplied package name with no alphanumeric character (`is_usable_anchor_name`). scip-python reports the project root package as `"."`, an emptiness check let it through, and the whole repo anchored on `.` — a concept titled `.` in `python_..md`, with `python_._src.md` beside it. Falling through to the manifest chain is strictly better than salvaging: `pyproject.toml` gives the real distribution name, and because markers sort deepest-first a repo whose examples carry their own manifests splits into those packages instead of collapsing into one.
