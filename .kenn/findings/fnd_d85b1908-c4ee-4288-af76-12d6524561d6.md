The CRAP gate MUST clean coverage artifacts before instrumenting: `cargo llvm-cov clean --workspace` is the first line of `just crap-ci`/`just crap`, not an optimization. Leftover `.profraw` from an earlier run merge into the next one and UNDERSTATE coverage, and the CRAP formula (cyclomatic^2 * (1-coverage)^3) amplifies that into a wall of phantom failures: 30 stale files cut the run from 37945 covered lines to 12163 and reported 229 "new over-threshold" functions in crates the change never touched. Verified: with 160 stale files AND a daemon up, the cleaned recipe still yields exactly 37945 — the gate is deterministic again.

The trap is the failure MODE, not the failure. It looks like a real regression (named functions, real line numbers, plausible CRAP scores), it lands in crates you did not touch, and re-running "fixes" it — which is precisely how a team learns to re-run a red gate instead of reading it. It fired twice in one session, each time right after an interleaved `cargo build` / `kenn index` had left fresh profraw behind.

Corollary for diagnosis: when the gate reports many offending entries whose `coverage` is 0.0, suspect the coverage DATA before the code. Check `grep -c "^DA:[0-9]*,[1-9]" tmp/lcov.info` against a known-good run — a 3x drop is stale-merge, not a regression. Do NOT reach for `just crap-baseline`; baselining phantom entries bakes the noise in permanently.
