MCP read handlers MUST query a persisted index/table; they MUST NOT build an index or create a table on the read path — no per-call CREATE TABLE / CREATE VIRTUAL TABLE, no full-corpus load to construct a transient index. Build indexes at write/open time instead. Example (the fix that motivated this): findings search is served by a persistent FTS5 index at `<derived_root>/findings.db` — a derived, NON-committed run artifact built at `FindingsStore::open` from the committed records and maintained on `flush` (supersede/tombstone update target lifecycle flags via cheap UPDATE). `search_findings` only queries it (bounded LIMIT, lifecycle filtered in SQL) and resolves only the top-`limit` records; it no longer rebuilds a transient in-memory FTS over all_findings per call. Because reads run concurrently (findings RwLock), the store holds no live rusqlite Connection — open a fresh read-only connection per read. Reads that merely scan records without building a table (find_directives, DAG walks) are tolerated for now but are candidates to move onto the persisted index.
