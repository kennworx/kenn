The build-time `stats` table (code.db) is the model for workspace counters: aggregate ONCE at indexing, the read path does zero DB aggregation. Shape rules: NARROW / long-format `(scope, key, subset, metric, value)` — never a wide one-column-per-metric table; a new metric/dimension/subset adds ROWS, not columns (the schema-drift test `graph_ddl_is_valid` pins the table name via names::code::STATS). `subset` is the lens: `internal`/`test`/`external` (disjoint partition, precedence external→test→internal) for entity metrics, `graph` for clustering counters; there is NO `all`/union subset — a grand total is summed in code from the partition (a few int adds), never stored and never a DB SUM/count. Two producers write via one `DbWriter::write_stats(&[StatRow])`: (1) `writer/finalize.rs::build_entity_stats` does GROUP BY (bucket, subset) over symbols/files/defs per language + packages per manager; (2) `kenn-analyze build_analysis_hook::graph_stat_rows` records graph-structure counters as a byproduct of clustering — per language (scope=language) `nodes`, `god_nodes` (god short_id IS a node id → attribute directly), `communities` and `anchors` (attributed to the PLURALITY language of their MEMBER nodes — anchor ids are a DIFFERENT id space from node ids, so never look an anchor_id/primary_anchor_id up in a node→language map; use the per-node `membership` records / group nodes by anchor_name); whole-graph (scope=global) `hierarchy_depth`, `cross_anchor_communities`. NOT raw edge counts (an edge spans two nodes / isn't symbol-sourced, so a per-language edge count is meaningless and irreconcilable). get_workspace_overview makes one stats() read and only RESHAPES rows (no count_table, SUM, GROUP BY on the read path); count_table survives only as the empty-snapshot presence check.
