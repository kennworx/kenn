Cache-volume ownership: a root-running provisioner must hand back BOTH writable depths. The toolchain volume is written by two kinds of container — host-side Swift provisioning (run_swift_provision) runs as ROOT because the swift image needs root to read and 'cp -a' the toolchain, while every indexer container runs '--user <uid>:<gid>' (docker_launcher, MountStrategy::SamePath). So every directory the root provisioner creates is root-owned, and a --user container writes at exactly TWO depths under the mount: '/t/<arch>' (a sibling language's own 'mkdir /t/<arch>/go') and '/t/<arch>/<lang>' (kenn_toolchain::cache create_dir_all's the language dir, then takes '.{version}.lock' INSIDE it). Chowning only the arch dir is the bug that HIDES: sibling languages start working so it looks fixed, but provisioning a second version of the SAME language still dies with an opaque EACCES instead of the actionable Install::Preprovisioned message. swift_provision_script chowns both; ensure_cache_volume's repair chown walks TWO levels ('/v/*/ /v/*/*/') and NEVER '-R' — that walks multiple GB of toolchain contents on every preflight, and those are only ever read. The repair exists so a volume an older kenn left root-owned heals on the next preflight instead of forcing the user to delete a multi-GB cache. The script uses 'set -e' + 'if/then', NOT '[ -d ] && chown' with a trailing ':' — the trailing ':' made a chown rejected under rootless Docker / userns-remap exit 0, reporting preflight SUCCESS and surfacing later as an unattributed EACCES from the first indexer container; and the '&&' form makes the false branch the loop's exit status, so an EMPTY volume would fail the run.
