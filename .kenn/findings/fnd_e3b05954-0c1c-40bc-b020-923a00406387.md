The store schema is a DERIVED artifact — when the honest fix needs a column, add the column. Do not contort a consumer into re-deriving something the schema should carry, and do not preserve on-disk compatibility: nothing migrates a kenn snapshot, `kenn index` regenerates it, and STORE_SCHEMA_VERSION exists precisely so an older snapshot reports a mismatch instead of failing at a SELECT with a missing column.

The mechanism, in order: add the field to the record in kenn-model, the column to the DDL in db/sqlite/schema.rs, the field to the Row type in api/types.rs, then BOTH the reader SELECT (reader/scan.rs — remember the positional index shift for every column after the insertion point) and the writer INSERT (writer/aggregate.rs — placeholder count too), and bump STORE_SCHEMA_VERSION. Then reindex with --force, because a plain `kenn index` skips an unchanged checkout.

This is not the version churn the project avoids while prototyping — that rule is about inventing WIRE_VERSION / -v2 names for shapes nobody consumes yet. STORE_SCHEMA_VERSION is the existing, load-bearing mechanism for exactly this, and declining to bump it is what turns a clean regeneration into a cryptic runtime error.
