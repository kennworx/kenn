Host-side Swift toolchain provisioning (provision_swift_from_image, crates/kenn-indexer/src/docker.rs) MUST be idempotent, visible, and MINIMUM-aware. swift-tools-version is a MINIMUM, not an exact version — a provisioned toolchain >= the pin satisfies it. (1) SELECT before provisioning: reuse the best provisioned swift via kenn_toolchain::select::best_compatible (prefer exact, else highest >= pin; cross-major allowed). The host preflight (busybox glob of /t/{arch}/swift/*/) AND the in-container entrypoint (ToolchainCache::provisioned_versions in kenn-toolchain/src/run.rs) apply the SAME best_compatible over the same cache, so they agree on which toolchain runs — a repo pinning 6.0 reuses a provisioned 6.3 and skips the ~5 GB swift:6.0 pull entirely. (2) ANNOUNCE before any pull and INHERIT the child stdio ('.status()', not '.output()') so 'docker pull' progress shows — a silent multi-GB provision is indistinguishable from a hang. (3) The Swift staging dir is DOT-prefixed ('.{version}.staging') so an in-flight/crashed provision is structurally excluded from BOTH enumerations (busybox '*/' glob and container read_dir both skip dotfiles); completeness rests on the atomic stage->rename. THE TRAP: 'swift docker hangs' is provisioning latency, NOT the Foundation.Process deadlock (build-tooling only, worked around via posix_spawn ProcessRunner + KENN_TOOLCHAIN_LIB) — misdiagnosed twice; diagnose with 'docker run --rm -v kenn-toolchains:/t busybox du -sh /t/*/swift/*'.
