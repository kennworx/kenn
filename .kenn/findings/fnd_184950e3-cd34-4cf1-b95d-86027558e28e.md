lightningcss gotchas for the css producer (`css/parse.rs`): (1) `StyleRule.loc.line` is 0-BASED — add 1 for kenn's 1-based def lines (verified: `.foo` on editor line 3 → `loc.line == 2`). (2) lightningcss has NO comment node in its AST (the `CssRule` enum has no `Comment` variant — comments are dropped), so "selector text + adjacent comments" for FTS/embeddings is obtained by scanning the raw SOURCE text for the `/* … */` block immediately preceding the rule's line; the embedding value lives in that comment, not the selector name. (3) Atomic extraction: iterate `style.selectors.0` → `sel.iter_raw_match_order()` → `Component::Class(c)`/`ID(i)` with the bare name at `c.0.as_ref()`; recurse into `style.rules.0` for CSS nesting (`&.active` contributes the atom `active` directly, no `&`-resolution needed for atomic nodes). Custom props: `Property::Custom(c)` with `c.name` (CustomPropertyName::Custom(DashedIdent)) keeping the `--` prefix. Parse with `ParserOptions{ error_recovery: true }` so a malformed tail still yields the valid rules.
