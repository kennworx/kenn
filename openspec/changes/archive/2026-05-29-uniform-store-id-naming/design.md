# Design — uniform store id naming

## The rule

| name | type | stable across runs? | API-visible? | purpose |
|---|---|---|---|---|
| `id` | numeric (u32) | **no** (rewritten each run) | no | in-run join key (today's `short_id`) |
| `pub_id` | string | **yes** | yes | stable identity |
| `<role>_id` | numeric (u32) | n/a | no | FK to another row's `id` |

A table's *own* key is always `id`. A reference to another row is `<role>_id`. Stable string identity is `pub_id` — except where the domain already has a meaningful stable string (`files.path`, `packages.name`), which we keep.

## Why `src_id`/`tgt_id` stay generic
Edge endpoints are polymorphic: `calls`/`type_use`/etc. are symbol→symbol, `contains` is module→**file**, `defined_in` is symbol→module/package, `imports` is module→module. A single endpoint column therefore can't be `sym_id` — it resolves against symbol *or* file *or* package depending on the row's `kind`. Generic `src_id`/`target_id` is correct.

## Search dataset after rename
Reads cleanly under the rule: `id` = volatile join key (the file-docs change relies on this being resolved against the correct dataset by row kind), `pub_id` = the symbol's API-visible public id (unchanged, same meaning as in the graph; empty on file rows), `embed_key` = the internal composite key for embedding reconciliation. `pub_id` thus means the same thing store-wide; the composite is named for its role rather than overloading `pub_id`.

## Out of scope
- **Derived-analysis datasets** (`analysis_god_nodes`, `analysis_flat_communities`, `analysis_anchored_hierarchy`, `analysis_node_membership`): they carry FK-to-node columns named `short_id` and domain ids (`community_id`, `parent_id`, `flat_community_id`). Left untouched this round.
- **Wire frames and MCP response JSON**: the producer JSONL field names and the MCP result field names are not renamed here — this is a store-column + `kenn-model` record-field change only. Aligning the wire/API is a possible follow-up.

## Migration
A column rename is a schema change, so existing snapshots must be regenerated by a reindex. **No `STORE_SCHEMA_VERSION` bump** — there are no users, so we change the shape in place rather than carry version-compat (a stale snapshot is simply reindexed by the developer). `add-file-level-docs` rebases onto these names after this lands.
