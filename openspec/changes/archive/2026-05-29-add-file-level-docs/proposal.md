## Why

C# file-level comments — file-purpose headers and namespace-leading comments — are completely lost today. The C# indexer only reads `ISymbol.GetDocumentationCommentXml()`, which returns structured `///` XML doc and nothing else: plain `//` and `/* */` headers are dropped, and `INamespaceSymbol.GetDocumentationCommentXml()` returns empty even when a `///` sits directly above the namespace (verified empirically — C# does not bind XML docs to namespaces). The result: a file whose header explains its whole purpose contributes zero searchable text.

We want that prose in the doc index. The capture mechanism is cheap (the trivia is already in hand during the per-tree walk), but the comment must (a) be extracted from syntax trivia rather than the documentation API, (b) be filtered so license/copyright boilerplate does not pollute search, and (c) flow into the *same* BM25 doc path as symbol docs so search stays one code path — now returning file hits alongside symbol hits.

## What Changes

- **Producer (C#)**: emit file-level comment trivia on `FileFrame` as a new `doc` **array** — the file-header block (leading trivia of the compilation unit's first token) plus each namespace declaration's leading comment, in source order. The producer stays policy-free: it emits all comment trivia (`//`, `/* */`), no filtering.
- **Consumer (Rust)**: a license/boilerplate filter drops entries matching well-known markers (SPDX-License-Identifier, `Copyright (c)`, `All rights reserved`, `Licensed under`, common GPL/Apache/MIT phrasings); survivors are joined and stored.
- **Store**: a new sparse `file_docs` dataset (one row per file that has a surviving doc), kept separate from `files` and from `symbol_docs` so file *sources* can later be indexed and queried independently.
- **Search**: file docs become `RowKind::Doc` rows in the search dataset, identified by **path** (`pub_id` empty) — filling the path-fallback identity column the schema already scaffolds; their `embed_key` is `filedoc:<lang>:<path>`. BM25 indexes them identically to symbol docs.
- **MCP**: BM25 search results return **file hits alongside symbol hits**, hydrating a path-identified doc row into a file result (path, language, doc snippet) rather than a symbol.
- **Schema**: **no `STORE_SCHEMA_VERSION` bump** (no users — we change the shape in place while prototyping); the new dataset means existing snapshots are regenerated by a reindex.

### Modified Capabilities
- `dotnet-stream-indexer`: `FileFrame` gains an optional `doc` string array carrying file-header + namespace-leading comment trivia.
- `index-store-db`: new sparse `file_docs` dataset (`file_id` → joined doc text); license-boilerplate filtering on ingest.
- `lance-search`: file docs emitted as path-identified `Doc` search rows feeding the existing BM25 doc index.
- `mcp-symbol-search`: search returns file results alongside symbol results.

## Impact

- **Wire format**: additive optional field on `FileFrame` (`doc`); old consumers ignore it.
- **Store schema**: new `file_docs` Lance dataset; **no `STORE_SCHEMA_VERSION` bump** (no users). Existing snapshots are regenerated by a reindex.
- **Search result shape**: MCP search responses may now include file rows; the result type must distinguish symbol vs file hits, and file hits hydrate via the files dataset (file and symbol ids are independent id spaces — see design D6).
- **Cross-language asymmetry (accepted)**: Rust file-level docs (`//!`) attach to the per-file module symbol and surface as *symbol* hits; C# (no per-file symbol) surfaces as *file* hits. We accept this — it mirrors the languages' structure — rather than migrate Rust `//!` into `file_docs` (see design D8).
- **No new external dependency**: trivia extraction uses Roslyn already referenced by kenn-dotnet; the license filter is a static string heuristic.
- **Out of scope**: indexing file *source bodies* (the `file_docs`-separate design leaves room for it as a follow-up); migrating Rust `//!` docs into `file_docs`.
- **Depends on `uniform-store-id-naming`**: this change lands **after** that rename and uses its final column names — `files.id`, `file_docs.file_id`, and the search columns `id` (volatile join), `pub_id` (symbol public id, empty on file rows), `embed_key` (composite reconciliation key).
