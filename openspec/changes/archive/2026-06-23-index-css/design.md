## Context

kenn's pipeline is SCIP-centric for code, with **markdown** already proving the
"sibling producer" pattern (design D1): markdown is discovered, parsed natively
in Rust, and emitted as `kenn_model` records directly — never entering the SCIP
`transform` chain — running in two phases against a post-code join barrier
(`markdown_phase1_unit` → barrier → `resolve_markdown_code_unit`). Everything
downstream of `kenn_model` records (node/edge/FTS/vec schema, embeddings, MCP
navigation) is producer-agnostic.

CSS slots into this same shape, with one structural twist that markdown does not
have, and one parser surprise the spike uncovered.

## The structural twist: usage is implicit and unauthored

Markdown links are **authored** — someone wrote `[text](order.rs)` or
`[[OrderHandler]]`; resolution just finds the target. CSS usage is **implicit**:
nobody wrote a link. A class is defined in CSS (`.btn-primary { … }`) and "used"
inside opaque string literals that **SCIP never captures**:

```
   CSS world                  CODE world (SCIP / symbol graph)
   .btn-primary  ◄──────??──── "btn-primary"  ← a string literal,
   (a real node)               invisible to rust-analyzer / scip-ts
```

So unlike md→code (target node exists, resolve it), CSS→usage must **mine usage
sites out of source text** — they exist as nodes/edges nowhere in the current
pipeline. The model is Tailwind's content scanner:

```
  raw source text ──► broad candidate extraction ──► ∩ class registry ──► keep
   className="btn        "btn","btn-primary",          .btn ✓ .btn-primary ✓
    btn-primary          "is","active","card"…          card ✓  (rest dropped)
    card"
```

The known-set intersection is what makes recall-first safe: a stray `"the"`
becomes an edge only if a rule `.the {}` exists. False positives are bounded by
the registry, not by parse precision — which is why a token scan beats a
per-language AST here, and why it satisfies the "all languages via globs"
requirement with zero per-language work. Context (`class=` vs incidental string)
is recovered by **grading**, not parsing: a registry match within N chars of
`class=`/`className=` → `Exact`; a bare match elsewhere → `Fuzzy`/`Ambiguous`.

## Goals / Non-Goals

**Goals:**

- Stylesheet classes/ids/custom-properties become first-class nodes/edges in the
  *same* graph as code, searchable and navigable via existing tools.
- A class registry with definition sites, doubling as the usage-scan known set.
- Usage edges code→class across **all configured languages** via `usage_sources` globs.
- CSS-internal dependency graph (`@import`/`@use`/`@extend`/`composes`).
- Orphan detection: dead classes, dead stylesheets, dangling code classes.
- Resolution that survives ambiguity: multiple defs of one class is normal
  (the cascade), keep-all is correct, not a failure.

**Non-Goals:**

- Computing specificity / cascade resolution (which rule "wins"). Out of scope.
- Usage/orphan tracking beyond **classes**. `uses_css_class` mines `class=`/
  `className=`/module members only; ids and custom properties are indexed as
  searchable definition nodes but have no usage mining (no `id=` scan, no
  var-use edge) and no orphan report in v1. (`#id` usage and `var(--x)` graphs
  are deferred.)
- Resolving dynamically-constructed class names (`btn-${variant}`,
  interpolation `.icon-#{$name}`) — unresolvable by any textual or AST means;
  recorded as misses, not chased.
- A full Sass compiler. kenn needs class/id/var names + locations + a handful of
  at-rule edges, not evaluated values.
- Incremental reindex (kenn has none; full rebuild stands).
- Vector production (owned by `incremental-embedding`; this only emits prose).

## Parser decision (driven by a spike)

A throwaway spike compared lightningcss, grass, tree-sitter-css, and
tree-sitter-scss against gnarly fixtures **and real source** from Bootstrap
(122 scss / 39 css), Bulma (182 scss / 40 css), and open-props (83 css).

### `.css` → **lightningcss** (decisive win)

- Parsed **162/162** real CSS files with zero failures.
- Typed, **atomic** extraction: `.btn.btn-primary` → two classes; custom-prop
  **defs** (`Custom(DashedIdent("--brand"))`) distinct from `var()` **uses**.
- `error_recovery: true` recovered a deliberately malformed/unterminated rule.
- open-props (custom-property-heavy): 1732 var defs cleanly extracted.
- Supports real **CSS Nesting** — `&` is resolvable by tracking the parent in
  the rule walk.

### `.scss` → **compile-primary (dart-sass CLI) + scanner fallback**

The decisive realization: a *source* parser/scanner — any of them — cannot see
classes generated by `@each`/mixins. Compiling Bootstrap yields **846** unique
atomic classes (`bg-opacity-25`, `bg-primary-subtle`, …) that exist only
post-compile, yet are exactly what markup writes. Without them, every usage of a
generated class falsely reports `Dangling`, poisoning the usage/orphan graph. So
for the registry, compilation is not a convenience — it is correctness.

| approach | complete? (incl. generated) | robust to partial/broken? | source locations? | cost |
|---|---|---|---|---|
| tree-sitter-scss 1.0 | ❌ no `!default`; no generated | ✅ tolerant (partial) | ✅ byte ranges | low |
| grass → lightningcss | ⚠️ Bootstrap ✅ / Bulma ❌ | ❌ all-or-nothing | ⚠️ sourcemap only | high |
| lightningcss direct | ❌ no Sass; mis-resolves `&` | ✅ | ✅ | low |
| purpose scanner | ❌ misses generated classes | ✅ by design | ✅ byte offsets | medium |
| **dart-sass CLI → lightningcss** | ✅ **incl. generated** | ⚠️ per-entry (mitigated) | ✅ **via source map** | medium |

Empirical detail that drove this (spike against the three corpora):

- **tree-sitter-scss** threw **21,376 ERROR nodes across 85/122** Bootstrap
  files — cause was **`!default`** (on nearly every variable line), plus
  `@use … as ns`/`@function`. The maintained grammar HEAD has **no rule for
  `!default`/`!global`** and only stubs `@use`/`@forward`. ERROR nodes also
  locally **corrupt the tree** (broke `&`-resolution inside `.card` while the
  clean `#sidebar` resolved). And it sees **zero** generated classes.
- **grass** (pure-Rust Sass) compiled Bootstrap but **failed Bulma**
  (`Undefined function: color.channel` — grass 0.13.4 lags the Dart Sass
  stdlib). Unfit as the backbone; usable later as an optional pure-Rust oracle.
- **dart-sass via the `sass` CLI** compiled **both** Bootstrap and **Bulma**
  (exit 0) — Bulma yielding 1937 unique atomic classes. With `--source-map`,
  lightningcss-located selectors **back-map to their origin partial**
  (`.theme-light` → `sass/utilities/css-variables.scss:39`; `.small` →
  `_variables.scss:625`). Full chain validated.
- **The Rust `sass-embedded` crate (0.7.1) is protocol-stale** — it panicked
  decoding modern dart-sass 1.100's embedded protocol (`invalid wire type value:
  7`). Conclusion: integrate via the **stable `sass` CLI** (kenn's existing
  sidecar pattern), not the embedded-protocol crate.

**Decision:** lightningcss for `.css`. For `.scss`/`.sass`, the **dart-sass
compiler is required — no bespoke fallback parser**:

- **dart-sass CLI sidecar (the only Sass path).** Discover entry points (non-`_`
  files at configured roots), compile each with `--source-map`, extract the
  atomic registry with lightningcss, and map selector locations back through the
  source map to the original `.scss`/`.sass`:line. This captures generated
  classes and yields reliable def sites, and dart-sass handles **both** syntaxes
  (`.scss` and indented `.sass`) natively — so `.sass` needs no special path.
- **On failure: skip + log, never hand-roll.** A `.scss`/`.sass` entry that
  fails to compile is skipped with a logged reason; one bad entry never sinks the
  run. We do **not** ship a hand-rolled Sass scanner — the spike showed that
  even real grammars/compilers (tree-sitter-scss, grass) get Sass wrong or
  incomplete, and a lexical scanner would be lossy *and* subtly incorrect
  (interpolation `#{}`, `@each` templates, cross-line selector lists, `&`-nesting
  under `@media` — our own spike's `&`-resolution already broke inside `.card`).
  A degraded mode, if ever needed, reuses lightningcss error-recovery over raw
  source (a real parser already in the tree), not new parser code.
- **At-rule graph via source scan.** Compilation resolves `@extend`/`@use`/
  `composes` away, so the CSS-internal dependency edges (Phase 3) come from a
  light source scan, not the compiled output. (This is keyword/line spotting,
  not Sass parsing.)

Requiring the compiler is not a new burden: a project with a Sass codebase
already has a Sass compiler. kenn discovers it from the **natural places a JS/Sass
project keeps it**, in order:

1. `node_modules/.bin/sass` (the project's dev-dependency shim);
2. the dart-sass shipped inside `node_modules/sass-embedded-<platform>/dart-sass/sass`
   and `node_modules/sass/...` (the `sass`/`sass-embedded` npm packages);
3. `sass` on `PATH` (global / system install);
4. a kenn-bundled `sass` per platform (like kenn-dotnet/kenn-ts), as last resort.

A configured override path wins over discovery. The cost is the source-map
plumbing; the payoff is a *correct* registry with no lossy parser to maintain.

## Pipeline shape

```
  PHASE 1  (parallel with code drivers)            CSS-internal graph (Phase 3,
  ─────────────────────────────────────            via light source scan — these
  .css → lightningcss                              at-rules are compiled away):
  .scss/.sass → dart-sass CLI --source-map →         @import/@use/@forward → imports (module→module)
                lightningcss  (compiler required;     @extend .x / composes → extends_rule (→class)
                failed entry → skip + log)            (@extend %placeholder, @include → deferred)
   → atomic class/id/var nodes (incl. generated)
   → def sites via source-map back-map
   → BUILD CLASS REGISTRY  (= known set)
        │
  ══════ CODE JOIN BARRIER ══════════════════════
        │
  PHASE 2  scan usage_sources files as TEXT
   → extract class-shaped candidates (Tailwind style)
   → ∩ registry → uses_css_class edges, graded by context  (HIT ONLY)
   → CSS-Modules (JS/TS): `import s from './x.module.css'; s.foo` pinned to that
     file (camelCase ↔ kebab fold) — precise, beats the global scan
   → no registry match → no edge/node; undefined tokens → check_css report only
        │
  PHASE 3  hygiene/orphan pass (reuse check_links machinery → check_css)
   → orphan class: defined, 0 inbound uses_css_class
   → orphan stylesheet: no used selectors AND no inbound imports
   → dangling code class: used, no def, not a known utility
```

## Key decisions & rationale

- **Two languages (`Css` + `Sass`), shared node kinds.** `Language` is
  source-file provenance (drives `prefix`/`db_name`/`extensions`/filtering), so a
  `.scss` file must not be tagged `css` — it is Sass, a superset with compilation
  semantics, and the spike's two processing paths (lightningcss vs dart-sass)
  fall on exactly that boundary. `.scss` and `.sass` are one language (two
  syntaxes) → `Sass`, not two more variants. The node *kinds*
  (`css_class`/`css_id`/`css_var`) and the class **registry** stay unified —
  "all stylesheet classes" is a query by kind, not language. The split costs a
  few extra `match` arms; the gain is honest provenance (esp. generated classes
  back-mapped into `.scss`) and `language: sass` vs `css` filtering.
- **Atomic class names are the unit, not resolved compound selectors.** Usage
  linking matches `className="card active"` → tokens `card`, `active` against
  atomic registry entries. Full `&`-resolved compounds (`.card.active`) are only
  needed for the CSS-internal/specificity view (Phase 3 nicety), not for the
  core usage/orphan goals. This is why even error-prone SCSS parsing would have
  *mostly* sufficed for Phase 2 — but the scanner gets atoms cleanly anyway.
- **Unmatched tokens produce no edge or node (revised).** An earlier draft made
  Tailwind utilities `Dangling` stub nodes; that was wrong — in a Tailwind repo
  it would create a stub + edge for *every* `flex`/`pt-4`/`mt-2` across every
  file, inflating the graph enormously (markdown's dangling case is rare; CSS's
  is the common case). Decision: `uses_css_class` edges are emitted **only on a
  registry hit**, so utilities (no definition) simply produce nothing. Undefined
  class-shaped tokens are collected into a *report* set for `check_css` (gated on
  a utility allowlist), never materialized as graph nodes. The edge grade now
  encodes only *match confidence* (`Exact`/`Fuzzy`/`Ambiguous`), not
  definedness.
- **Stylesheet files are `module` nodes.** Each `.css`/`.scss` file is a
  `Kind::Module` node that `contains` its selectors (`defined_in`), so `@use`/
  `@import`/`@forward` are honest `imports` (module→module) edges — no overload
  of the existing edge contract, and orphan-stylesheet detection ("a module with
  no inbound `imports` and no used selectors") falls out. The typed native ID
  `<lang>:<relpath>#<type>:<name>` keeps a class and an id of the same name in
  one file distinct.
- **One `CssConfig` for both languages.** Even though `Language` splits
  `css`/`sass`, the *config* is unified — `roots`/`usage_sources`/`excludes` are
  shared; only Sass-only knobs (compiler override, load paths) live in a nested
  `sass` subsection. Excludes default-deny `dist/`/`build/`/`node_modules/` so
  compiled CSS isn't indexed alongside its Sass source (double-counting). A
  utility registry seeded from `tailwind.config` (so utilities resolve to a
  synthetic node instead of being dropped) is a deferred enhancement.
- **`usage_sources` is explicit (default empty), not broad.** A repo is often a
  monorepo where only some projects use CSS; a broad default would scan unrelated
  code on every reindex (wasted work) and invite false matches. So usage mining
  is opt-in: the user declares which sources consume CSS classes. Phase 1
  (parse/registry/search/dependency graph) is independent of `usage_sources` and
  runs regardless — enabling CSS gives a fast, bounded "stylesheets are now
  searchable" immediately; pointing `usage_sources` at real consumers turns on
  the usage graph. Two guards make the empty default safe: (1) a one-time hint
  when `usage_sources` is unset, so the marquee feature isn't *silently* off;
  (2) orphan-class detection is gated on `usage_sources` (else every class has
  zero inbound usages and `check_css` would flag them all) — it skips that
  category and says why. Orphan-*stylesheet* detection (via `imports`) is
  unaffected.
- **Multiple defs of one class → `Ambiguous` keep-all is semantically correct.**
  Under the cascade, `.btn` defined in 3 files genuinely all apply. The markdown
  resolver's keep-all-on-tie + `nearest_by_locality` tiebreak port directly.
- **`usage_sources` mirrors Tailwind's `content`.** A new `[language.css]` config
  block (sibling to `MarkdownConfig`) carries stylesheet `roots` (what to parse)
  and `usage_sources` globs (what to scan for usage), all raw pattern strings
  compiled to `GlobSet`. Usage scanning is independent of which code languages
  are SCIP-indexed — it is pure text over globs.
- **No new SCIP work; usage edges are mined, not derived from SCIP.** SCIP has
  no class-string nodes; trying to extend the SCIP indexers to capture string
  literals was rejected as high-cost and language-specific. The text scan is the
  whole point of the Tailwind model.
- **Code→stylesheet imports are recovered in the Rust barrier, not the code
  indexer.** A `.css`/`.scss`/`.sass` import has no code declaration, so the code
  indexers (kenn-ts, etc.) drop it — and they *cannot* re-add it: wire edges are
  numeric `Ref`s siloed per producer, with no cross-producer symbol table and no
  stub for unresolved targets, so a kenn-ts edge to a CSS node minted by the Rust
  producer can never resolve. The only cross-producer mechanism is the post-code
  store-lookup barrier where `resolve_css_usage` already runs. So that barrier
  also scans `usage_sources` files for stylesheet import specifiers (identified
  **by MIME type** via `mime_guess`, already a dep), resolves each relative
  specifier to a stylesheet `module` node, and emits a module→module `imports`
  edge from the importing code module. Reuses `EdgeKind::Imports` (same contract
  as CSS-internal `@use`/`@import` and code module imports) — `list_imports`
  stays uniform; a stylesheet's inbound importers may be stylesheets or code,
  told apart by source language. Missing target → no edge (no stubs);
  non-relative/aliased specifiers are out of scope (path-mapping lives in the
  code indexer, which can't carry the edge). This is the file-level mirror of the
  class-level `uses_css_class` graph.

## Risks / open questions

- **dart-sass is a hard dependency for Sass indexing.** No bespoke fallback, so
  if no `sass` is found and none is bundled, `.scss`/`.sass` are not indexed.
  Mitigation: a Sass codebase already ships a Sass compiler (discover it on
  PATH / `node_modules/.bin`); optionally bundle one per platform like the other
  sidecars. Absence is an install/build condition, logged clearly — not silent.
- **Entry-point discovery & load paths.** Compilation needs entry files, not
  partials, plus `@use`/`@import` load paths. Mitigation: treat non-`_`-prefixed
  stylesheets at configured roots as entries; configurable load paths; an entry
  that fails to compile is skipped with a logged reason (not partially indexed).
- **Generated-class def-site granularity.** A class from an `@each` loop
  back-maps to the loop line, not a unique authored selector — so orphan
  reporting for generated classes is coarser (can't say "this one iteration is
  dead"). Acceptable; authored classes keep precise sites.
- **Non-language `usage_sources` file types don't trigger reindex yet.** The
  watcher keys off `Language::extensions()`, so editing a `.tsx` re-mines usage
  (TypeScript is a language) but editing a future `.html`/`.vue` template would
  not. Accepted: HTML/Vue/other web-framework templates are planned follow-ups,
  and their watcher integration lands with them; until then non-language content
  is refreshed on full reindex. Usage *mining itself* is already language-
  agnostic (raw-text globs), so adding a file type is a glob + a watcher entry.
- **Broken / in-progress Sass yields nothing until it compiles.** Without a
  fallback parser, a file mid-edit that fails to compile is skipped. Accepted
  deliberately: a lossy hand-rolled scanner would be *subtly wrong*, which is
  worse than absent for a transient state. lightningcss error-recovery over raw
  source is the escape hatch if this ever bites — no new parser.
- **`@use` namespacing & load paths.** `@use 'x' as ns; ns.$var` and
  `composes: a from './b.module.css'` reference other files. Phase 3 resolves
  these against the building store (post-barrier), reusing the md→code
  locality/keep-all ladder. Cross-file `@extend` of an imported placeholder may
  stay `Ambiguous`; acceptable.
- **Dangling-code-class noise.** The "used in code but undefined" report is only
  trustworthy once a utility allowlist exists (Tailwind/3rd-party classes are
  legitimately undefined-in-repo). Ship the orphan-*class* and orphan-*sheet*
  reports first; gate dangling-code-class on the allowlist.
- **`.sass` (indented syntax).** Bulma ships 3. The scanner must handle
  indentation-significant syntax or skip `.sass` in v1. Decision pending corpus
  weight; lean skip-with-warning in Phase 1.
- **CSS-in-JS** (styled-components, Emotion, `css\`…\``) defines classes inside
  code, not stylesheets. Out of scope for v1; the usage scan still catches
  *string* class usages, just not template-literal *definitions*.
- **`@extend %placeholder` is out of scope, not just unimplemented (decided
  after real-repo validation).** The source scan emits `extends_rule` only when
  the enclosing rule is a sole bare class. Measured on Bootstrap + Bulma, the
  dominant `@extend` enclosings are exactly the forms the scan can't resolve:
  Bulma interpolates every selector (`.#{$prefix}name`), and Bootstrap extends
  `%heading` from element selectors (`h1`–`h6`). So indexing placeholder nodes
  would add a node kind + a Sass source-level node producer for ~zero additional
  edges, and `@extend` is compiled away so the output can't recover it either.
  `extends_rule`'s real yield is in CSS-Modules `composes` (sole-class by spec,
  no interpolation) and non-interpolated `@extend .class`. Park placeholders
  until a codebase with sole-bare-class `@extend %x` justifies the work.
